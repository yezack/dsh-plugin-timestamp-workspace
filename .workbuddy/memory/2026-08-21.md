## 修复 slot 冲突（single slot already has a registration at priority 0 (registered by x6)）
- 症状（重启后第二段报错）：`failed to apply loader entry ... single slot "conversation.hero.workspace.directoryFlow" already has a registration at priority 0 (registered by x6)`
- 根因：宿主 ui-workspace 的 x6 注册（registrant "x6"）已占用两个 single directory-flow hole（`conversation.hero.workspace.directoryFlow` / `sidebar.workspaces.directoryFlow`）的 priority 0；我们的插件同样以默认 priority 0 register 即冲突。slot 系统（@deepseek-ai/dsh-client-ui-slots）规则：single slot 同 priority 重复注册 throw；priority 升序、最低渲染（cell shadowing rank）。
- 修复：`src/client.ts` apply 中两个 `ctx.slots.register` 均加 `priority: -1`，shadow x6（保留宿主触发入口与 adoption 语义，occupant 拥有 open→picked 交互）。
- 部署：commit 7c872c8 已 push；profile 内 lib/client.js 已更新（grep priority: -1 命中 2 处）；新 tgz 已打包。
- 通用知识点：dsh slots API——`register({name, inject, priority}, renderer)`，host 声明 hole 用 `children`；`inject(name, fn)` 向已声明 slot 注入。single slot shadow 必须换 priority。

## 新增设置面板分区（settings.section，wallet 风格）
- 需求：用户看到其他插件（deepseek-harness-wallet 等）在 dsh 设置面板有分区，要求本插件也有 UI 配置 rootDirectory（不再手改 yaml）。
- 机制（wallet 零依赖参考实现）：宿主 Settings shell 通过 `settings.section` slot 渲染插件分区；插件客户端 `ctx.slots.inject('settings.section', () => ctx.slots.register({name:'settings.section', id, order, label: ()=>'时间戳工作区', inject: ()=>({})}, SectionComponent))`；服务端 `inject:['webServer']` + `ctx.webServer.register({kind:'exact', path:'/api/<ns>/settings', handler})`（wallet 用 `/api/wallet/*`）；持久化到 `$DSH_HOME/storages/<ns>.json`（tmp+rename 原子写）；客户端组件直接 `fetch('/api/<ns>/settings')` 读写（宿主 api-proxy 不 serve 第三方 namespace，必须走插件自己的 fenced route）。
- 本插件实现：服务端 GET/PUT `/api/timestamp-workspace/settings`，store 优先于 yaml 配置（重启后 UI 设置保持）；Config.rootDirectory 改 optional（schemastery 字段默认 optional，`.required()` 才必填——**注意 schemastery 无 `.optional()` 方法**）；客户端 settings.section id='timestamp-workspace' order 60，组件含"选择目录"（闭包引用 apply 时保存的 ctx.workspaces.pickDirectory()）+ 手输 + 保存；directoryFlow 对话框 open 时 fetch 最新 root。
- 测试：test/verify-server.mjs（mock webServer，GET/PUT/校验/持久化/重启 store 优先）+ verify-client.mjs 扩展 settings.section 检查。

## 修复 settings fetch 404（服务端路由从未注册）
- 症状：设置面板报 `settings fetch failed: 404`；curl 实测 `GET /api/timestamp-workspace/settings` 404，而 wallet 的 `/api/wallet/snapshot` 200。
- 根因（关键协议坑）：profile 的 `cordis.patch.yml` 里插件条目写成 bare 形式 `- dsh-plugin-timestamp-workspace: {rootDirectory: ...}`，宿主 patch loader 拒绝：`patch: id is required for non-insert patches` → **服务端插件从未被 cordis 加载** → webServer 路由不存在。客户端 UI 却能正常显示，因为 web 端 bundle 是自动扫描 node_modules 里带 dsh.client 字段的包（不走 patch），两条加载路径独立——**这是 client 正常而 server 404 的原因**。
- 修复：条目改为 insert 形式（wallet 同款）：
  ```yaml
  - insert:
      - id: timestamp-workspace
        name: dsh-plugin-timestamp-workspace
        config:
          rootDirectory: C:/Users/yezac/Documents/dsh-workspaces
  ```
- 验证：`dsh --profile web --dump-config`（npx 缓存路径 `AppData/Local/npm-cache/_npx/<hash>/node_modules/@deepseek-ai/dsh/lib/bin.js --profile web --dump-config`）可看 patch 合并结果与报错；改后 `- id: timestamp-workspace` 出现在树里，报错消失。
- **patch 是热更新的**：改完 cordis.patch.yml 无需重启服务，路由立即 200（GET 返回 yaml 值，PUT 持久化到 storages 后 GET 返回 store 值）。
- 产物：commit ffa9d29 已 push（README 修正为 insert 示例）；README.md/README.zh.md 已同步部署副本。
- 通用知识点：**dsh patch 顶层条目只有两种合法形式——`{id: ...}`（targeted override/disable，无 id 报错）和 `{insert: [...]}`（新增插件/服务，元素须含 id+name+config）**；bare `- <pkg>:` 会被拒。诊断插件服务端是否加载：dump-config 看树 + curl 插件 fenced route。

## 新建对话默认继承"上一次文件夹"的根因与修复（c534af4）
- 用户诉求：新建对话默认不选择文件夹。
- 根因（宿主内置，非插件行为）：`dsh-client-runtime`（npx 缓存 `_npx/<hash>/node_modules/@deepseek-ai/dsh-client-runtime/lib/client.js`）的 `WorkspaceRuntime.startSession(workspaceId)` 解析链 `workspaceId ?? currentWorkspaceId ?? recentWorkspaceId`——顶栏/hero 区"新建对话"无参调用 → 继承 `recentWorkspaceId`（"最近更新的会话所属 workspace"，由 `project()` 投影计算）。无任何 slot 能拦截该默认。
- 修复：插件 client 端 apply 时 **monkey-patch 存活服务对象**：`originalStartSession = ws.startSession.bind(ws)`，替换为——无参调用直接 `ws.sessions?.clear?.()`（进入无工作区的新会话视图）；有参调用（sidebar 某 workspace 内新建会话）透传原逻辑。模块级 flag 保证 HMR 重复 apply 幂等。
- 可行性依据：宿主 UI（dsh-client-ui-sidebar 258 行、ui-workspace 2354 行、agent-preset 1646 行）全部是 `startSession: (id) => ctx.workspaces.startSession(id)` 运行时动态查对象属性，替换对象方法即全局生效。
- 验证：test/verify-client.mjs 新增无参 clear / 有参透传 / 重复 apply 幂等断言，全过。
- 注意：应用启动时 `startInitialSelection()` 仍会自动连 recent workspace（用户未抱怨，未改）。push 当时网络故障（schannel SSL 失败），commit c534af4 需后续重试 push。

## 启动时也抑制自动选择最近工作区（5145063，push 待重试）
- 用户诉求：启动时也不要自动打开"上一次文件夹"，与新建对话一致。
- 根因确认：`WorkspaceRuntime.startInitialSelection()` 在宿主 runtime apply 内**同步执行**（cordis fiber effect），插件 apply 之前已启动：`initialSelectionStarted=true`，reconcile 订阅 `list` 等首个 ready 基线；冷启动无恢复会话（`sessions.list.current === undefined`）且 `recentWorkspaceId` 有值时自动 `connectWorkspace(target)` 并 open。方法替换/重置标志都够不到已创建的 reconcile 闭包。
- 关键：`recentWorkspaceId` 是**纯客户端投影**（`project()` 里 `recentWorkspace(workspace.items, sessions.byId)`，按会话 updatedAt 取最新，无配置可关）。消费点仅 4 处：初始值/投影写入/启动 reconcile/原版 startSession（已被替换覆盖）。
- 修复（方案：投影遮蔽）：插件 apply 时包装 `ws.list.set`——**首个 `baselinesReady===true` 投影**且 `sessions.current===undefined` 时把 `recentWorkspaceId` 抹成 undefined 再透传，然后**立即恢复原 setter（一次性）**。reconcile 读到 target undefined → `state="done"` 不 connect。后续投影正常透传，不影响"最近工作区"UI。模块级 flag 幂等。
- 注意：`list` 是 createSnapshotStore（zustand createStore，`set: (next) => api.setState(next, true)` 整体替换），`current` 字段在 `sessions.list` 不在 workspace 快照里——判断要用 `ctx.workspaces.sessions.list.getSnapshot().current`。包装 set 时直接解构原函数调用（箭头函数不依赖 this）。
- 验证：verify-client.mjs 新增——首个 ready 投影抹掉 recentWorkspaceId、后续投影透传、重 apply 不重复包装，全过；verify-server.mjs 过。已部署 profile lib/client.js。
